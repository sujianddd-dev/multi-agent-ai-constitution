# 架构规范（ARCHITECTURE）

> 本文件描述系统的**结构、模块边界与架构决策原则**。
> 架构是"已批准的宪法条款"——修改必须走审批流程。

---

## 🏗️ 系统结构

```
project/
├── README.md                    ⭐ 共享协议（宪法总纲）
├── AGENTS.md                    ⭐ Agent 入口（社区标准）
├── .github/
│   └── CONTEXT.md              ⭐ 项目上下文
├── ARCHITECTURE.md             ⭐ 架构规范（本文件）
├── AGENT_GUIDELINES.md         ⭐ Agent 行为准则
├── API_CONTRACT.md             ⭐ 接口约定
├── CODING_STANDARDS.md         ⭐ 代码标准
├── DECISION_LOG.md             ⭐ 决策历史
└── modules/
    ├── backend/                # 后端服务
    ├── frontend/               # 前端应用
    └── tests/                  # 测试套件
```

> 📌 `modules/` 子目录**按需创建**（当前为规划占位）；空目录不会进入 Git，
> 需要保留占位时在目录内放一个 `.gitkeep` 文件。
> 按实际项目形态调整（如浏览器插件项目可改为 `extension/ + core/ + tests/`），调整须记录决策日志。

## 🧩 模块划分与职责

| 模块 | 职责 | 边界（不得越界） |
|---|---|---|
| `backend/` | 业务逻辑、API 实现 | 不直接操作前端资源 |
| `frontend/` | 用户界面、交互 | 不包含业务规则 |
| `tests/` | 单元/集成/E2E 测试 | 不修改被测代码逻辑 |

## 📐 架构原则

1. **单一职责**：每个模块只做一件事
2. **依赖方向**：只允许上层依赖下层，禁止反向依赖
3. **接口稳定**：public API 一经发布即冻结（见 API_CONTRACT.md）
4. **最小变更**：优先做局部修改，不做全局重构
5. **可测试性**：核心逻辑必须可脱离 UI/网络独立测试

---

## 🧩 协议优先（架构第一原则）

> 系统首先是一串**协议**（接口、事件、数据契约），每个协议背后是可替换的实现。
> 依据：工程信条《DOCTRINE》§0、§4。

**三条硬性要求：**

1. **协议先行**：跨模块 / 跨进程 / 跨 Agent 的交互，**先落协议**（接口签名、事件 schema、数据结构、错误语义），再写实现
2. **协议是唯一契约面**：实现可替换、可并行重写；**协议变更必须显式批准**（见 [API_CONTRACT.md](./API_CONTRACT.md)）
3. **边界即上下文边界**：每个模块的协议文档应**自足**——Agent 只读它就能改它，不必读遍全系统（**解耦就是控制上下文预算**）

**反模式**：模块之间绕过协议直接读对方存储；把实现细节写进协议（实现一换，协议就废）。

---

## 🪄 聚合展现（表现层纪律）

> 表现层是**聚合者**：按当前任务把若干协议的结果临时组织成一次输出。

1. 表现层**不承载业务规则**（规则在协议 / 服务侧）
2. 同一份数据允许多种视图（人类摘要 / Agent 结构化证据 / 监控指标），**视图可临时生成**——这正是 token 擅长的事，不必固化
3. 视图生成失败**必须可降级**，不能让"好看的视图"成为可用性单点

---

## 🚫 架构红线

- ❌ 不允许 Agent 私自修改已批准的架构
- ❌ 不允许绕过分层直接访问数据层
- ❌ 不允许在未记录决策的情况下引入新模块
- ❌ 不允许把业务规则写进表现层
- ❌ 不允许绕过协议直接读写其他模块的存储

---

## ✍️ 架构变更流程

> 权限依据：README「治理结构」审批权矩阵（人类 ✅；主 Agent 需人类批准；普通 Agent ❌）。

1. 在 [DECISION_LOG.md](./DECISION_LOG.md) 提议变更（写明原因与影响）
2. 等待**人类批准**（主 Agent 提议的变更同样需要人类批准）
3. 批准后更新本文件 + CONTEXT.md 的相关章节
4. 再开始实施

> **未经批准修改架构 = 违反宪法。**
