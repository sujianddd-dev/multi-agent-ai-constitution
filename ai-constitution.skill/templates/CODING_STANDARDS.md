# 代码标准（CODING_STANDARDS）

> 所有 Agent 提交的代码必须符合本文件要求。格式问题由审查者一票否决。

---

## 🎯 总体原则

1. **可读性优先**：代码是写给人看的，顺便给机器执行
2. **最小惊讶**：遵循语言惯用写法，不炫技
3. **防御式编程**：外部输入必须校验
4. **注释解释"为什么"**，不解释"是什么"

---

## 📐 语言与格式

| 项目 | 规范 |
|---|---|
| 语言 | 以 CONTEXT.md 技术栈为准 |
| 缩进 | 4 空格（Python）/ 2 空格（JS/TS） |
| 行宽 | 不超过 120 字符 |
| 引号 | 统一单引号（Python）/ 双引号（JS/TS） |
| 结尾 | 文件末尾保留一个空行 |

---

## ✍️ 命名规范

- 变量 / 函数 / 文件：`snake_case`
- 类：`PascalCase`
- 常量：`UPPER_SNAKE_CASE`
- 布尔变量：`is_` / `has_` / `can_` 前缀
- 禁止：拼音命名、无意义缩写（`a`、`tmp1`）

---

## 📝 注释要求

- 公共函数/类必须有 docstring，说明：作用、参数、返回值、异常
- 复杂逻辑必须有行内注释解释"为什么这样写"
- TODO 必须标注负责人与截止时间：`# TODO(agent-name): ...`

---

## 🧪 测试要求

- 新增功能必须配套单元测试
- 测试命名：`test_<被测函数>_<场景>`
- 覆盖边界条件与异常路径
- 提交前必须本地跑通：`pytest`（或项目规定的测试命令）

### TDD 节奏（依据工程信条《DOCTRINE》§3）

1. **先写失败测试**：把"怎样算做对了"变成可执行断言，再写实现
2. **修复缺陷必须先有复现测试**：没有复现测试的修复视为**未完成**
3. **测试是验收锚点的一部分**：项目验收命令必须能一条跑完（见 STATE.md「✅ 验收」）
4. 反模式：断言过弱（只验证"不报错"）、只测 happy path、写完实现再补"看起来很全"的测试

---

## 📤 提交（Commit / PR）规范

**Commit message 格式：**

```
<type>(<scope>): <subject>

<body: 做了什么、为什么、影响>
```

- type：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- scope：模块名（如 `backend`、`api`）
- subject：祈使句，不超过 50 字符

**提交粒度与回滚（依据《DOCTRINE》§3）：**

- **一个 PR 只做一件事**——便于 `revert`、便于归因、便于 review
- 每个 PR 必须能回答："**这个改动坏了怎么退回？**"（命令 / 步骤）
- 数据 / schema 变更：可逆，或前置备份 + 回滚脚本，并在 PR 中说明"**半失败怎么办**"
- 禁止把无法回滚的变更直接推进 `main`

**PR 描述必须包含：**

- [ ] 变更内容摘要
- [ ] 关联的规范文档（CONTEXT / API_CONTRACT 等）
- [ ] 测试情况
- [ ] 不确定/待确认事项

---

## ✅ 提交前自检清单

- [ ] 通过所有测试
- [ ] 遵循命名规范
- [ ] 添加了必要注释
- [ ] 无未使用的导入/变量
- [ ] 无调试残留（print/debugger）
- [ ] 更新了相关文档
- [ ] 未违反 API 合同
