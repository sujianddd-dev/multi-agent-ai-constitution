# 设计依据（WHY）— 共享知识库为什么是 Agent 与人类协作的核心基础

> **起源记录：2026-08-14。** 本文是这套"AI 宪法"的设计根据、权衡分析与边界说明。
> 一句话结论：**用文档做协调中枢（单向读取），而不是让 Agent 互相通信（双向协商）。**

---

## 一、问题：多 Agent × 多模型的协调成本

一台电脑里可能同时存在 zcode、Codex、Claude Code、Kimi Work……
背后是 KimiK3、GLM5.3、DSV4F、Claude 等不同模型。它们各自拥有：

- 各自的会话历史与记忆（**互相不可见**）
- 各自的指令文件约定（`AGENTS.md` / `CLAUDE.md` / 工具私有配置）
- 各自的工具集、权限与上下文窗口

于是"怎么切换、怎么迁移、怎么沟通"变成日常摩擦。而**真正的损失不是切换本身，是切换时丢失的进度上下文**：新接手的 Agent 不知道上一手做到哪、为什么这么做、下一步是什么、踩过哪些坑。

---

## 二、两种解法的对比

| 对比 | 完全自由协作（Agent 互相通信） | 共享 Context 方案（本文） |
|---|---|---|
| 协调成本 | 高（要约定协议、处理时序与失败重试） | 低（**单向读取**，无需通信） |
| 一致性 | 低（各自决策，容易分叉） | 高（统一指导，读同一份"剧本"） |
| API 成本 | 高（通信本身 = 额外模型调用） | 低（一次性写文档，反复读取） |
| 可维护性 | 差（协议散落在各 Agent 的提示词里） | 好（文档在仓库里，可版本化、可 review） |
| 可扩展性 | 难（N 个 Agent 需要 N² 条通道） | 容易（**加一个 Agent = 它读一遍文档**） |
| 异构模型 | 几乎不可行（不同厂商模型无法共享内存） | 天然可行（都能读 GitHub 上的 Markdown） |

```
┌────────────────────────────────┐
│   Shared Context & README      │  ← 所有 Agent 的"宪法"（Truth Source）
│   （README / CONTEXT / STATE） │
└────────────────────────────────┘
     ↑                    ↑
  Agent A             Agent B
 （读取规范）         （读取规范）
     ↓                    ↓
  按规范执行          按规范执行
     ↓                    ↓
  提交 PR             提交 PR
```

---

## 三、为什么它对"异构模型"特别有效

1. **GitHub 是唯一所有模型都能访问的中立存储**——不绑定任何厂商、任何工具、任何机器的本地记忆。
2. **自然语言 Markdown 是唯一所有模型都懂的接口**——没有私有提示词语法，没有 SDK 版本问题。
3. **版本控制自带可追溯性**——谁在什么时候、依据哪条规范、做了什么，全部沉淀为 PR 与 DECISION_LOG，人类也读得懂。

> 这个方案 = 编程的"版本控制" + AI 的"思想统一"。

---

## 四、五步落地

```
Step 1: 建立"共享宪法"（README + 若干指导文档）
        ↓
Step 2: 所有 Agent 都要读这些文档（入口标准化：AGENTS.md + 全局协议层）
        ↓
Step 3: Agent 在约束下工作（只读，无需互相通信）
        ↓
Step 4: 提交 PR 时引用相关规范（PR 即交接单）
        ↓
Step 5: 人类或主 Agent 审批 merge
        ↓
完成！低成本、高效、可控
```

---

## 五、边界与代价（诚实说明）

这套方案不是银弹，它的已知代价与对策：

| 风险 | 表现 | 对策（本仓库的落地方式） |
|---|---|---|
| **文档滞后** | 文档说"A 在做"，实际已换人/已改向 | `STATE.md` 接力棒 + 铁律"**每轮收尾必须更新，不更新=本轮未完成**" |
| **不读就动手** | 新 Agent 跳过文档直接改代码 | 全局协议层（`~/.dsh/AGENTS.md` 等）+ 项目根 `AGENTS.md` + 首轮交接自检清单 |
| **进度靠自觉** | 换模型后质量漂移 | 宪法里写死**一条与模型无关的验收命令** + PR 里贴结果 |
| **本地记忆冒充事实源** | 某工具的 memory/会话历史被当成进度依据 | 约定：本地记忆**只能当加速器，不得当交接依据**（Truth Source 唯一） |
| **不替代实时协商** | 复杂决策需要讨论 | 需要协商的走 PR 评论 / 人类裁决；文档只承载**已定事项** |

---

## 六、与"实时通信型"方案的分工

生态里另一种思路是让子 Agent **互相发消息、共享任务看板**（例如 DSH 的 agent-teams 类插件）。两者不冲突：

- **实时通信型**：适合同一进程内、同构运行时、短周期的并行协作。
- **文档共识型（本仓库）**：适合**异构 Agent + 异构模型 + 跨机器**的长期项目——它们无法共享内存，但都能读 GitHub。

对"电脑里一堆 Agent、背后一堆模型"的场景，**文档共识型才是基础设施**；实时通信型是它之上的可选项。
