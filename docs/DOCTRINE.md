# 工程信条（DOCTRINE）— 协议优先 · 灰度闭环 · 迭代严谨 · 风险有护栏

> **分工**：[WHY.md](./WHY.md) 回答"为什么用文档做协调中枢"；**本文回答"工程怎么做"**。
> **性质**：本文是**总则**（不随项目变）；具体可填条款落在 `templates/` 各文件的对应章节，见文末「落地映射」。
> **适用**：所有采用本宪法的项目——无论是产品、工具链还是文档库本身。

## 零、总纲：软件 = 协议优先的微服务 + 灵活聚合的表现层

**主张**：系统首先是一串**协议**（接口、事件、数据契约），每个协议背后是可替换的实现；**表现层是聚合者**，按当前任务把若干协议的结果临时组织成一次输出。

**为什么**：

- **协议是唯一稳定层**：实现会换代，协议可以长期不动。协议稳定 → 换实现不需要协调所有下游。
- **解耦就是控制上下文**：模块边界 = 上下文边界。Agent 只需加载"它要改的那份协议"，而不是整个系统的全部细节——**上下文预算就是最稀缺的资源**。
- **聚合展现要灵活**：表现层固化是浪费。同一份协议数据，按任务临时组织（给人类的摘要、给 Agent 的结构化证据、给监控的指标）——**这恰好是 token 擅长的事**：让"每次生成一个合适的视图"变得便宜。

**反模式**：把业务规则沉到表现层（下一个视图就得重写一遍）；模块之间直接读对方存储（协议被绕过，边界名存实亡）。

## 一、理念：不回到重型前置规划

**主张**：计划只做到"**下一个可验证增量**"，不预先规划所有分支。

| 项 | 内容 |
|---|---|
| 要做的 | 明确"这次要动哪个数 / 交付什么可见结果" → 立刻做最小可验证版本 → 用数据决定下一步 |
| 不要做的 | 先写全量设计矩阵、接口清单、把可能的分支全规划好才动手；把"文档齐全"当成开工前提 |
| 与文档的关系 | **不重型前置 ≠ 不写文档**：契约、ADR、决策是**增量沉淀**（做完就记），不是开工仪式 |
| 验收 | 任何任务应能在**首个工作时段内**产出可运行 / 可验证的增量；超时说明该拆了 |

> 判据：计划文档如果比代码还长，且没有一行被验证过——已经回到重型前置了。

## 二、方法：MVP + 灰度数据闭环决定方向

**主张**：方向由**数据**决定，不由直觉或会议决定。任何面向真实使用者的行为变更，都必须先回答四个问题（四要素缺一不可）：

| 要素 | 必须回答 | 反模式 |
|---|---|---|
| **1 指标** | 这次改哪个数？成功线 / 失败线各是多少？（1 个北极星 + ≤2 个护栏指标） | 改完才说"感觉快了" |
| **2 分层采样** | 放量维度与阶梯（内部 dogfood → 1% → 10% → 50% → 100%）；每级观察多久 | 一次全量上线 |
| **3 归因** | 出现变化时怎么归因（对照 / 前后对比 / 混淆因素清单）；**改动前的自然波动是多少** | 把自然波动当成本次成效 |
| **4 关门阈值** | 触发**停止放量并回滚**的硬条件（错误率、性能、资金与数据安全）；阈值**提前**写死 | 事后解释"虽然有波动但总体还行" |

**纪律**：

- 四个问题在**动手前**写下来（写进 PR 描述或 `STATE.md` 的灰度行），事后补写的不算
- 每一级放量都要有明确的"继续 / 停止"判据；没有判据就不许进入下一级
- 关门阈值一旦触发，**回滚优先于分析**（先止血，再归因）
- MVP 的"M"是"最小可验证"，不是"最省事"——不可验证的 MVP 不是 MVP

## 三、工程：迭代内部仍要严谨（快 ≠ 糙）

**主张**：可以小步快跑，但每一步内部必须工程严谨。四个硬面：

| 面 | 要求 | 落点 |
|---|---|---|
| **契约：IO 事务管理** | 跨边界调用显式定义输入 / 输出 / 错误；写操作必须有**事务边界**与**幂等**设计（重试安全、可去重）；跨系统写要说明"半失败怎么办" | `templates/API_CONTRACT.md`「IO 事务与幂等」 |
| **测试：TDD** | 先写失败测试，再写实现；修复缺陷必须先有复现测试；验收命令是唯一锚点 | `templates/CODING_STANDARDS.md`「TDD 节奏」 |
| **可观测：ADR** | 每个架构级决策留一条 **ADR**（= 本宪法 `DECISION_LOG.md`）：背景 / 决策 / 原因 / **被否决的方案** / 影响 | `templates/DECISION_LOG.md`（明示 = ADR） |
| **回滚：git** | 每个变更可回滚：小 PR、单一主题、可 `revert`；数据 / schema 变更要么可逆，要么前置备份与回滚脚本 | `templates/AGENT_GUIDELINES.md`「回滚」 |

**判据（自检三问）**：这个改动**坏了怎么退回**？**凭什么说它对**？**下一手怎么知道为什么这么做**？三问答不上来 = 还不够严谨。

## 四、架构：协议优先 + 聚合展现

**主张**：先定协议，再写实现；表现层保持可替换的聚合。

**协议优先的三条硬性要求**：

1. **协议先行**：跨模块 / 跨进程 / 跨 Agent 的交互，先落协议（接口签名、事件 schema、数据结构、错误语义），再写实现
2. **协议是唯一契约面**：实现可以替换、可以并行重写，协议变更必须走**显式批准**（见 `templates/API_CONTRACT.md`）
3. **边界即上下文边界**：每个模块的协议文档应当**自足**——Agent 只读它就能改它，不需要读遍全系统

**聚合展现的三条纪律**：

1. 表现层**不承载业务规则**（规则在协议/服务侧）
2. 同一份数据允许多种视图（人类摘要 / Agent 结构化证据 / 监控指标），**视图可临时生成**
3. 视图生成失败必须可降级（不能让"好看的视图"成为系统可用性的单点）

## 五、风险管理：承认 vibecoding 的「隐蔽负债」，流程必须有护栏

**主张**：AI 高速产出的代码"**看起来能跑**"，负债藏在看不见的地方。承认它，然后用护栏兜住，而不是靠感觉。

**隐蔽负债的六种典型形态**（自查清单）：

1. **隐式假设**：依赖了未写下的前提（数据有序、字段必存在、网络必通）
2. **缺测试 / 假测试**：测试只覆盖 happy path，或断言过弱（等于没测）
3. **错误处理缺失**：异常路径静默吞掉或直接崩
4. **边界未定义**：空值、超长、并发、重复提交没约定
5. **依赖幻觉**：引用了不存在 / 版本不匹配的 API（编译过 ≠ 运行对）
6. **复制粘贴漂移**：同一逻辑多处实现，改一处漏一处

**分级响应 playbook**（三级，每级三要素缺一不可）：

| 级别 | 触发条件（可观测、可判定） | 处置动作 | 复盘防复发 |
|---|---|---|---|
| **P0 红线** | 数据丢失 / 资金受损 / 安全漏洞 / 隐私泄漏 / 不可逆误操作 | **立即**停止放量与写入 → 回滚 → 通知人类 → 保留现场证据 | 24h 内写 ADR：根因 + **防复发动作**（加护栏 / 加测试 / 改流程） |
| **P1 严重** | 核心功能不可用；指标越过**关门阈值**；错误率 / 延迟显著劣化 | 暂停放量 → 定位（先回滚止血，后分析）→ 热修或保持回滚 | 48h 内记 ADR + 补复现测试 + 明确"下次如何更早发现" |
| **P2 一般** | 局部异常、体验退化、非核心路径失败 | 登记 issue（含复现步骤）→ 排期修复 → **不阻塞**当前发布 | 汇总进下轮复盘；同类问题重复出现则升级为 P1 处理 |

**两条铁律**：

- **护栏必须写下来**：触发条件、处置动作、责任人与时限——没写下来的护栏等于没有
- **复盘必须产出防复发动作**：只写结论（"下次注意"）不算复盘；必须落到测试、护栏、流程或文档

## 反模式速查（一眼识别违规）

- ❌ 还没写下指标与关门阈值就开始改
- ❌ 一次全量上线，没有分层放量阶梯
- ❌ 用"看起来对 / 感觉快了"代替验收命令的结果
- ❌ 一个大 PR 混多个主题（不可回滚、不可归因）
- ❌ 决策只记结论，不记**被否决的方案**与原因
- ❌ 业务规则写进表现层；模块绕过协议直接读对方数据
- ❌ 修复没有复现测试；复盘没有防复发动作
- ❌ 把"文档齐全"当成开工前提（重型前置）
